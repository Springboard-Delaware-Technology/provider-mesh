## 5. Delegated repair and hard stops

Within an approved mission, the Agent may choose compliant internal methods and correct ordinary formatting, lint, type, build, test, verifier, development-workflow, and Preview failures. It may update stale tests to match approved behavior, use an already installed dependency through a supported interface, and make the bounded migration corrections in §9. No additional approval is needed for those delegated actions.

For a failed command: identify the root cause, determine whether the correction is delegated, apply the correction, rerun the narrowest relevant check, and continue. Count repeated unsuccessful attempts at the **same root cause**, not the number of commands or sequential defects. Stop after three unsuccessful attempts at that root cause unless the approved specification sets another limit, or earlier if the correction becomes materially ambiguous.

Preserve the unconditional hard stops in Governance §11. Stop affected work for a human decision when:

- The required change crosses the approved mission or an excluded capability, changes business meaning, or encounters a material conflict in controlling documents.
- An identity, authority, confidentiality, organizational-isolation, ownership, evidence, audit, or data-integrity invariant cannot be preserved.
- Real personal information appears in a synthetic-only environment; production access, public exposure, or protected processing is required without its authority; or a secret appears in a file, prompt, log, test, output, or commit.
- A dependency addition or upgrade, lockfile change, runtime change, deployment change, port change, or security-configuration change is required outside prior authorization.
- A migration partially applies, unexpected database objects or ledger entries appear, an applied migration would need rewriting, or destructive recovery is required outside an approved procedure.
- Repository changes are unexplained or unauthorized, supply-chain trust or required access permissions are unresolved, or the permitted repair limit is exhausted.

Do not lower acceptance thresholds, weaken validation or deny-by-default behavior, remove meaningful tests, or broaden coverage exclusions to obtain a passing result. A failed command alone is not a hard stop. Authorized reauthentication or the established human-assisted Git route may resolve an authentication failure; neither permits bypassing an access denial or obtaining broader authority.

For a hard stop, report the actual blocker, the governing provision, the smallest decision needed, and the current repository/environment/recovery state. Do not turn an unrelated future improvement into a blocker.

## 8. Git, authentication, commits, and synchronization

### 8.1 Preflight and branches

At the start of a new implementation package, establish the repository, branch, HEAD, upstream, fresh remote state, ahead/behind count, staged and unstaged diff, untracked non-ignored files, and absence of unintended attachments or secrets in the delivery boundary. Confirm a clean synchronized starting state before Class C implementation.

`main` is the established controlling branch. Work on the branch authorized for the task and confirm it before committing. The direct pushes used for approved document storage do not grant standing permission to push future work to `main`. This control imposes no new branch, pull-request, or merge requirement; use the approved mission's workflow and any existing repository protection.

After a successful fresh fetch, the established main-branch verification is:

```bash
git branch --show-current
git rev-parse HEAD
git rev-parse origin/main
git rev-list --left-right --count HEAD...origin/main
git status --short
```

For this command's argument order, the first count is local-ahead and the second is local-behind. An empty status is clean; `0 0` means the two references match. Use the applicable upstream for another approved branch and preserve any separate merge requirement. For a newly created approved branch without an upstream, report that fact and establish its approved base against the freshly fetched controlling branch. Do not report an old remote-tracking reference as fresh remote evidence.
