## 3. Round 1 — review of draft revision 4 (verbatim reviewer report)

> **Verdict: Not ready — blocking defects.** Five blocking items; all are bounded textual repairs, not redesign.
>
> **Blocking defects**
>
> **B1. No environment class for the deployment that hosts public discovery (L176, L199, L222).** §6.1 defines exactly three environments and puts Production "after the public-discovery gate at the earliest," while §6.3 rule 2 puts the public-discovery stage on the development platform's managed deployment. Public discovery necessarily receives unsolicited real personal text (SEC-ID-01; replit.md §6; Constitution §9.4). A publicly exposed service receiving real personal information cannot be a development-class environment (SEC-DEV-01; Governance §12.1) and §6.1 rule 3 forbids exposing development-class deployments as a service. Fix: state that the deployment hosting public discovery is the production environment, operating under the reduced profile until protected data arrives, and correct the "Stage of use" cell.
>
> **B2. SEC-PLAT-01's "dependency ownership" and "patching" are neither decided nor deferred.** The ADR quotes both at L31 and claims coverage in §16 (L401, "SEC-PLAT-01 → §6–§11"), but the only mention is the P4 rejection rationale (L192). §3.2 gives them no home. SEC-PLAT-01 is a "must" directed at this ADR.
>
> **B3. Contradictory audit write privilege (L155 vs L276).** §5.3 requires an "append-only write identity distinct from the application runtime"; §8.2 grants the application runtime "insert-only on audit." §13 item 4 asks Foundation 001 to prove the runtime cannot alter audit rows. Two engineers would build different audit paths; the §8.2 reading weakens SEC-AUD-04's separation.
>
> **B4. Privileged authentication weaker than SEC-ID-04 (L221, L229, L264–265).** SEC-ID-04: "Privileged control-plane access must use phishing-resistant authentication." Both profiles and §8.1 rule 1 require only MFA; nothing in the ADR requires phishing-resistant authentication. §8.1 rule 2 also drops "stronger authentication," which SEC-PRIV-02 lists among the conditions for person-specific troubleshooting.
>
> **B5. §6.5 selects a database product the ADR says it does not select (L243).** "Springboard-owned managed **Postgres** project" contradicts §3.2 (L91), §13 item 1 (L355, Foundation 001 must "name the … relational database product"), and §14, which records no such decision. Architecture §7.4 requires product selection to be made in an ADR — so either record it as a decision with alternatives, or say "a managed relational database (product named in Foundation 001)."
>
> **Ordinary repairs**
>
> - **L47, L349:** "The analytic environment is physically separate" is attributed to Arch §15.14 and Security §20. Arch §15.14 says "distinct"; SEC-SECONDARY-02 permits separation "whether logically or physically implemented under the deployment design." Physical separation is this ADR's own (stricter, permissible) choice — move it out of "what the controlling documents already fix" and into §14.
> - **L301:** "key revocation renders retained ciphertext unreadable" overstates protection. SEC-RET-03 forbids treating cryptographic erasure as interchangeable with deletion without validation; per-object data keys "stored alongside the ciphertext" do not establish per-record erasure.
> - **L133:** "Custodian Organization" and "contributing Organization" are not Domain Model concepts. DM §5.1 defines Organization / Organization Unit / Organization Capacity; custodianship is defined at DM §13.1 for documents.
> - **L366 (and L63):** the development-seed guard is cited to Governance §12.4; the controlling provision is §12.1 ("An environment guard must prevent a development-only verifier or destructive test from running against production"). L63 says the guard is carried forward into "§6.1 rule 1 and §8.3," but neither rule states it — the ADR never states the guard as a rule.
> - **L152 vs L134–135:** "All four dimensions on every protected row" contradicts §5.1, where Collaboration and Springboard-capacity references are conditional.
> - **L294:** §9.1 rule 1 delegates cipher configuration to the platform; SEC-PLAT-02 requires the approved profile to *specify* acceptable protocol/cipher configurations. Name the source and record it at the gate.
> - **L204, L243, L344:** the "plan change, not a data migration" consequence presumes the chosen provider offers a contractually protected tier reachable on the same project. State it as a requirement on the selection. Vendor-shaped terms ("project," "branch restore," "tier") sit close to replit.md §1; make them capability descriptions.
> - **L332:** SEC-RET-04's "restore into a restricted environment" step is missing from the restore rule.
> - **L208:** Governance §12.4 covers post-application verification, not a startup schema-state assertion.
> - **L358, L388:** renumber §13 item "3a"; "items 1–12" then resolves cleanly.
>
> **Future improvements**
> Define "restricted field group" (§9.2). Constrain compute location, not only store location, in the reduced profile (L216–223). Add the SEC-AUD-03 durable buffering path for audit-sink unavailability.
>
> **Citation spot-check**
> 62 checked, 57 correct. Incorrect or overstated: L47, L349 (Arch §15.14 / Security §20), L133 (DM §5, §8), L208 and L366 (Governance §12.4). Imprecise but not wrong: L44 drops SEC-ORG-02's "without server validation" (§5.4 rule 1 is stricter, so no conflict). Gate names in §15, decision IDs in §3.2, and all Foundation 001 item cross-references in §2.4 resolve correctly. Tables are structurally valid (all column counts consistent).
>
> **SEC-PLAT-01 coverage**
> Production/nonproduction boundaries — addressed §6.1 (defective, B1). Tenancy — §4, §5. Data locations — §7. Network entry/exit — §10. Runtime and storage identities — §8.2. **Dependency ownership — missing.** **Patching — missing.** Encryption — §9. Monitoring — §6.5, §11 rule 3 (vendor assessment deferred to SEC-PLAT-05). Backups — §11 rule 1, §6.5. Recovery — deferred with a stated home (§3.2 → SEC-D13 / production runbooks); restore test retained at §11 rule 1. Vendor-access paths — §8.1 rule 6, §6.4.

The drafter verified the reviewer's cited provisions (`SEC-ID-01`, `SEC-ID-04`, `SEC-AUD-03`, `SEC-AUD-04`, `SEC-SECONDARY-02`, `SEC-RET-03`, `SEC-RET-04`, Governance §12.1 and §12.4, Domain Model §5.1) against the controlling documents before applying repairs.
